# 06 计费与资金规则（碰到钱必读）

> 本文件是钱相关逻辑的**唯一依据**。写代码时逐条对照，测试用例按第 10 节逐条写。
> 文档没写到的资金场景：**停下来**，记到 `PROGRESS.md` 的「待确认问题」，不要自己发明规则。

---

## 1. 两种币

| 币 | 谁持有 | 怎么来 | 怎么用 | 能否提现 |
|---|---|---|---|---|
| 金币 | 男用户 | 后台客服充值、任务奖励、后台补发 | 付费私信、送礼物、买会员 | 不能 |
| 积分 | 女用户 | 私信分成、礼物分成、任务奖励、后台补发 | 提现 | 能 |

- 金币和积分**分开记账**，各有钱包表和流水表，永远不互相转换。
- 都是**整数**，不允许小数。
- 比例统一用**万分比整数**：`3000` 表示 30%，`10000` 表示 100%。
- 女用户没有金币钱包入口（App 不显示），男用户没有积分钱包入口。

## 3. 私信计费规则

### 3.1 谁付费

- 男 → 女：可能付费，按 3.2 判断。
- 女 → 男：**永远免费**，女用户也不拿积分。
- 同性之间：禁止发送（错误码 30003）。

### 3.2 判断顺序（`MessagePricingService::quote(maleId, femaleId)`，按顺序判断，命中就停）

```
1. 双方互相关注 且 chat.mutual_follow_free = 1      → 免费，原因 MUTUAL_FOLLOW
2. 这对男女之间男方已发送的条数 < chat.free_count_per_pair → 免费，原因 PAIR_FREE
3. 男方是有效会员 且 今天已用会员免费条数 < vip.daily_free_messages → 免费，原因 VIP_FREE
4. 以上都不满足                                      → 收费，价格 = 女方当前等级的私信单价
```

- 第 2 步「已发送的条数」= 该男用户发给该女用户的全部消息条数（不管是否免费），存在会话表的 `male_sent_count`。
- 第 3 步「今天」按 `Asia/Shanghai` 自然日，计数存 Redis（key `vip_free:{userId}:{yyyyMMdd}`），并在 `cl_message` 记录免费原因，方便对账。
- 价格取**发送那一刻**女方的等级，写进消息记录，之后女方升级不影响旧消息。

### 3.3 扣费与分成（`MessageBillingService::send`，**一个数据库事务内完成**）

```
1. 校验：双方状态正常、异性、没被拉黑、内容合法
2. 幂等：client_msg_id 已存在 → 直接返回已有消息，不重复扣费
3. 调 quote() 得到 price、free_reason
4. 如果收费：
   a. 锁男方金币钱包行（lockForUpdate）
   b. 余额 < price → 抛错误码 20001（余额不足），整个事务回滚，消息不发送
   c. CoinWalletService::decrease(男方, price, type=MESSAGE, ref=消息ID)
   d. 计算女方积分（见 3.4），PointWalletService::increase(女方, points, type=MESSAGE_INCOME, ref=消息ID)
   e. 平台收入记一条：platform_coins = price，user_points = points
   f. 女方累计收益增加后，调 LevelService::checkUpgrade(女方)
5. 写消息记录（price、free_reason、share_rate、points 都要存）
6. 会话表 male_sent_count + 1，更新最后一条消息
7. 事务提交后：WebSocket 推送给女方；返回消息和最新余额、下一条报价给男方
```

### 3.4 积分计算公式

```
分成比例 rate = 女方等级的私信分成（万分比）
如果 女方未实名：rate = rate × share.unverified_factor ÷ 10000（向下取整）

积分 points = floor( price × rate × point.per_yuan ÷ ( 10000 × coin.per_yuan ) )
```

例：Lv1 单价 5 金币，已实名，rate 3000：`floor(5 × 3000 × 100 ÷ (10000 × 10)) = floor(15) = 15 积分`（= 0.15 元，男方花 0.5 元，平台留 0.35 元）。
例：同上但未实名，rate = 1500：`floor(7.5) = 7 积分`。

- 只用整数运算，先乘后除，最后向下取整。用 PHP 的 `intdiv()`，不准用浮点。
- points 为 0 也照常记录消息，但不写积分流水。

### 3.5 退费

**不退费。** 消息发出即扣费（R5-2）。只有后台管理员可以手动补偿（见第 8 节）。

## 4. 礼物

- 只有男用户能送，只能送给女用户。
- 价格 = 礼物表的 `price_coins`（送出那一刻的价格写进赠送记录）。
- 流程同 3.3：一个事务内扣金币 → 女方加积分 → 平台收入 → 检查升级 → 写礼物记录 → 在会话里插一条礼物消息（`type=GIFT`，这条消息本身**不再按私信收费**，也不计入 `male_sent_count`）。
- 积分 = `floor( price × share.gift_rate × point.per_yuan ÷ (10000 × coin.per_yuan) )`；如果 `share.unverified_apply_gift = 1` 且女方未实名，rate 先乘未实名系数。
- 幂等：`client_order_id` 唯一。

## 5. 等级

- 等级只属于女用户（男用户等级字段固定为 1，不使用）。
- `LevelService::checkUpgrade`：女方 `total_earned_points`（累计收益积分，只增不减，提现不减）达到某级门槛 → 升到满足条件的最高等级。**只升不降。**
- 后台可以手动调整等级，并可以勾选「锁定等级」（`level_locked = 1`）：锁定后自动升级不再生效。手动调整写操作日志（谁、何时、从几级到几级、原因）。
- 升级时给女方发一条系统通知。

## 6. 会员

- 只有男用户能开通（女用户 App 不显示会员中心）。
- 开通方式：
  1. App 内用金币购买套餐：事务内扣金币（type=VIP）→ 延长 `vip_expire_at`（未过期则在原到期时间上加天数，已过期则从现在开始加）→ 写会员订单。
  2. 后台客服开通：选套餐或直接填天数，写会员订单（来源 = ADMIN，金币 0），必须填备注。
- 有效会员 = `vip_expire_at > 当前时间`。
- 权益：每日额外免费私信（3.2 第 3 步）、看完整访客（P08）、看完整喜欢我（P09）、VIP 标识。会员**不抵扣礼物**。

## 7. 每日任务

任务表 `cl_task` 字段：名称、描述、图标、类型、目标值、奖励数量、适用性别（男/女/全部）、周期（每日/一次性）、排序、启用。

| 类型 code | 完成条件（服务端判断） | 默认奖励 |
|---|---|---|
| `SIGN_IN` | 今天点了签到 | 男 5 金币 / 女 20 积分（两条任务记录，各自适用性别） |
| `PROFILE_PHOTO` | 相册审核通过的照片 ≥ 目标值（默认 3），一次性 | 男 20 金币 / 女 50 积分 |
| `PROFILE_BIO` | 自我介绍审核通过，一次性 | 男 10 金币 / 女 30 积分 |
| `SEND_MESSAGE` | 今天给 ≥ 目标值（默认 3）个不同的人发过消息 | 男 5 金币 / 女 20 积分 |

- 「领取」时服务端重新判断完成条件；同一周期只能领一次（唯一索引：用户 + 任务 + 周期日期）。
- 奖励：男方走 `CoinWalletService::increase(type=TASK)`，女方走 `PointWalletService::increase(type=TASK)`。任务奖励积分**不计入**升级用的累计收益（`total_earned_points` 只统计私信和礼物分成）。

## 8. 后台充值与调整

- **充值**（客服）：选用户（只能是男用户）→ 填金币数量（正整数）、实收金额（元，可填 0 表示赠送）、支付方式备注（微信/支付宝/其他）、备注 → 二次确认 → 事务内 `CoinWalletService::increase(type=RECHARGE)` + 写 `cl_recharge_order`（记录操作员 ID）。
- **金币扣减**（仅超级管理员）：填数量和原因，余额不能扣成负数，type=ADMIN_DEDUCT。
- **积分补发/扣减**（仅超级管理员）：同上，type=ADMIN_ADJUST。补发不计入累计收益。
- 所有后台资金操作都写 MineAdmin 操作日志。

## 9. 提现

### 9.1 申请（女用户，`WithdrawService::apply`，一个事务）

```
1. 校验：女用户、账号正常、withdraw.need_real_name=1 时实名已通过
2. 校验档位：金额（元）在 withdraw.tiers 里，且 ≥ withdraw.min_yuan
3. 校验次数：今天已申请次数 < withdraw.daily_limit（驳回的也算次数）
4. 需要积分 = 金额 × point.per_yuan
5. 锁积分钱包；可用积分 < 需要积分 → 错误码 20002
6. 手续费（元，保留两位小数，用「分」为单位的整数计算）= 金额分 × fee_rate ÷ 10000，向下取整；实际到账 = 金额 − 手续费
7. PointWalletService::freeze(女方, 需要积分)：可用 −，冻结 +，写流水 type=WITHDRAW_FREEZE
8. 写提现单：状态 PENDING，记录金额、积分、手续费、实到金额、收款方式、收款账号、收款人（= 实名姓名）
```

### 9.2 审核（财务）

| 操作 | 状态变化 | 积分变化 | 流水 type |
|---|---|---|---|
| 通过 | PENDING → APPROVED | 不变（仍冻结） | — |
| 驳回（必须填原因） | PENDING/APPROVED → REJECTED | 冻结 − ，可用 +（原路退回） | `WITHDRAW_REFUND` |
| 标记已打款（必须填打款流水号或备注） | APPROVED → PAID | 冻结 − （真正扣掉），`total_withdrawn_points` + | `WITHDRAW_PAID` |

- 状态只能按上表流转，其他流转一律拒绝（错误码 40001）。
- 每次状态变化都给女方发系统通知。
- 同一张单并发操作要加锁（`lockForUpdate` 提现单行）。

## 10. 必须有的测试场景（后端，一条场景至少一个测试）

**私信计费**
1. 前 3 条免费，第 4 条扣 Lv1 单价 5 金币，女方 +15 积分。
2. 后台把 `chat.free_count_per_pair` 改成 0，第 1 条就扣费。
3. 互相关注后发送免费；关闭 `chat.mutual_follow_free` 后恢复收费。
4. 会员每日 10 条免费：第 11 条开始扣费；第二天重新计数。
5. 判断顺序：互关免费时，不消耗会员当天的免费额度（命中第 1 步就停）；对子免费条数没用完时，也不消耗会员额度。
6. 余额 4 金币，单价 5 → 返回 20001，余额仍是 4，消息不存在，女方积分不变。
7. 同一 `client_msg_id` 发两次 → 只扣一次。
8. 并发：余额 10 金币，同时发 3 条单价 5 的消息 → 只成功 2 条，余额 0，绝不出现负数。
9. 女 → 男发消息：不扣任何钱，不加任何积分。
10. 男 → 男发消息：返回 30003。
11. 未实名女方：分成打五折（7 积分）。
12. 女方 Lv3：单价 10，分成 4000 → 40 积分。
13. 被拉黑后发送失败且不扣费。

**礼物**
14. 送 120 金币礼物：男 −120，女 +`floor(120×3400×100/100000)` = 408 积分。
15. 余额不足送礼物 → 20001，什么都不变。
16. 礼物消息不计入 `male_sent_count`。

**等级**
17. 累计收益跨过 20000 → 自动升 Lv2，并发通知。
18. 一次跨两级 → 直接升到最高满足的等级。
19. 锁定等级后不再自动升级。
20. 任务奖励积分不计入累计收益。

**会员**
21. 金币购买月卡：扣 390 金币，到期时间 +30 天；未过期续费在原到期时间上加。
22. 余额不足购买 → 20001。

**提现**
23. 未实名申请 → 被拒。
24. 档位不在配置里 → 被拒。
25. 积分不足 → 20002。
26. 当天第 2 次申请（limit=1）→ 被拒。
27. 申请后可用减少、冻结增加。
28. 驳回后积分原路退回。
29. 已打款后冻结减少、累计提现增加。
30. 已打款的单不能再驳回；已驳回的单不能再打款。

**后台**
31. 客服给男用户充值 → 余额增加、有流水、有充值单、有操作人。
32. 给女用户充值金币 → 被拒。
33. 扣减金币不能扣成负数。

**对账**
34. 任意一组操作后：金币钱包 `balance` = 该用户全部金币流水 `change` 之和；积分钱包 `balance` = 全部积分流水 `change` 之和，`frozen` = 全部积分流水 `frozen_change` 之和（字段见 04 文档）。写一个 `ReconcileTest` 随机操作 100 次后校验。
